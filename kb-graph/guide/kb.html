Znalostní báze projektu v grafu

Graf má dvě vrstvy: strukturu vygenerovanou z kódu (moduly, služby, trasy nginx, portlety, endpointy, tabulky, poznámky) a ručně psané lekce (pasti z poznamky/07, koncepty z poznamky/05) ukotvené na strukturu.

Na každém dalším slajdu je blok s dotazem: tlačítko Execute in Query tab (▶) ho rovnou spustí, Edit in Cypher editor ho jen vloží do editoru. Výsledek uvidíš jako graf; záložkami Graph / Table / Raw nad výsledkem ho zobrazíš i jako tabulku.

Uzel (kroužek) má label (barva) a vlastnosti; vztah (šipka) má typ a směr.

1. Jeden uzel a jeho sousedé

Začni u služby Redis: kdo na ni míří a kam míří ona. Uvidíš uzly různých labelů (Service, Lesson, Concept) a šipky s typem vztahu – závislosti z docker-compose i lekce, které jsou na Redis ukotvené.

Cypher: MATCH, uzel s labelem a vlastností, vztah bez směru

MATCH (n:Service {id: 'redis'})-[r]-(m)
RETURN n, r, m

2. Topologie běhu

Všechny služby z docker/docker-compose.yml a jejich depends_on. Graf vznikl z kódu – kdo změní compose, po dalším load uvidí změnu tady, aniž by cokoli psal ručně.

Cypher: filtrování podle labelu a typu vztahu, směr šipky

MATCH (a:Service)-[r:DEPENDS_ON]->(b:Service)
RETURN a, r, b

3. Cesta požadavku od nginx po tabulku

Strangler v jednom obrázku: nginx posílá /crm/ do nové aplikace a vše ostatní (/*) do Liferay, obě aplikace sahají do stejných tabulek sdílené databáze.

Cypher: cesta (path) jako proměnná p, řetězení vzorů

MATCH p = (:Service {id: 'nginx'})-[:ROUTES]->(:Route)-[:PROXIES_TO]->(:Service)
          -[:DEPENDS_ON]->(:Service {id: 'postgres'})-[:OWNS]->(:Table)
RETURN p

4. Co spadne, když spadne Redis?

Hvězdička znamená „přes libovolný počet kroků“. Dotaz najde i nepřímé závislé – nginx na Redis sám nezávisí, ale závisí na crm-web, který ano. Grep tohle neodpoví jedním příkazem.

Cypher: proměnná délka cesty *, tranzitivní závislosti

MATCH p = (s:Service)-[:DEPENDS_ON*]->(:Service {id: 'redis'})
RETURN p

5. Co přebuildovat po změně modulu

Obdoba dotazu z článku: po změně sso-portal-api je třeba přebuildovat všechny moduly, které na něm závisejí přímo i nepřímo. Hrany DEPENDS_ON vznikly z pom.xml.

Cypher: proměnná délka cesty nad moduly Maven

MATCH p = (m:Module)-[:DEPENDS_ON*]->(:Module {id: 'sso-portal-api'})
RETURN p

6. Pasti k tématu session a kam míří

Ručně psané lekce (Lesson) visí na tématu (Topic) a jsou ukotvené na strukturu z kódu. OPTIONAL MATCH vrátí i lekce bez kotvy – ty se týkají jen původního projektu.

Cypher: OPTIONAL MATCH, propojení dvou vrstev grafu

MATCH (t:Topic {id: 'session'})<-[:ABOUT]-(l:Lesson)
OPTIONAL MATCH (l)-[a:ANCHORED_TO]->(x)
RETURN t, l, a, x

7. Na co si dát pozor, když měním crm-web

Lekce ukotvené na modul crm-web, jeho endpointy, jejich soubory nebo službu, která se z něj builduje. To je otázka, kterou si klade agent před úpravou souboru: „co bych měl vědět o tom, na co sahám?“

Cypher: WHERE se vzorem, výsledek jako tabulka

MATCH (m:Module {id: 'crm-web'}), (l:Lesson)-[:ANCHORED_TO]->(x)
WHERE x = m
   OR (m)-[:DECLARES]->(x)
   OR (m)-[:DECLARES]->(:Endpoint)-[:DEFINED_IN]->(x)
   OR (x)-[:BUILT_FROM]->(m)
RETURN DISTINCT l.id AS lekce, l.title AS nazev, labels(x)[0] AS kotva, x.id AS na
ORDER BY lekce

8. Legacy koncept → náhrada a kde je vidět

Mapa konceptů z poznamky/05 jako graf: koncept Liferay (side legacy) vede přes REPLACED_BY na náhradu ve Spring Boot a SEEN_IN ukazuje, kde se v demu vyskytuje před a po migraci.

Cypher: více OPTIONAL MATCH, vlastnost v podmínce

MATCH (c:Concept {side: 'legacy'})-[r:REPLACED_BY]->(t:Concept)
OPTIONAL MATCH (c)-[s1:SEEN_IN]->(pred)
OPTIONAL MATCH (t)-[s2:SEEN_IN]->(po)
RETURN c, r, t, s1, pred, s2, po

9. Legacy koncepty, které demo neukazuje

Koncepty bez hrany SEEN_IN – demo je nepokrývá, na reálném projektu je třeba je ověřit zvlášť.

Cypher: negace vzoru WHERE NOT

MATCH (c:Concept {side: 'legacy'})
WHERE NOT (c)-[:SEEN_IN]->()
RETURN c.name AS koncept, c.description AS popis
ORDER BY koncept

10. Nejprovázanější poznámky

Kolik lekcí a odkazů míří na každou poznámku z poznamky/. Kde začít číst, když přicházíš na projekt.

Cypher: agregace count, ORDER BY, LIMIT

MATCH (n:Note)
OPTIONAL MATCH (n)<-[r:DESCRIBED_IN|LINKS_TO]-()
RETURN n.id AS poznamka, n.title AS nazev, count(r) AS odkazu
ORDER BY odkazu DESC, poznamka
LIMIT 5

11. Srovnání se SQL

Otázka z dotazu 4 jako tabulka jmen. V relační databázi by hrany byly tabulka depends_on(source, target) a tranzitivní uzávěr by potřeboval rekurzivní CTE – v Cypheru stačí hvězdička.

Cypher: proč graf – stejná otázka v Cypheru a v SQL

MATCH (s:Service)-[:DEPENDS_ON*]->(:Service {id: 'redis'})
RETURN DISTINCT s.id AS sluzba
ORDER BY sluzba

Totéž v SQL (jen pro srovnání, nespouští se):

WITH RECURSIVE dependants(id) AS (
    SELECT source FROM depends_on WHERE target = 'redis'
  UNION
    SELECT d.source FROM depends_on d JOIN dependants x ON d.target = x.id
)
SELECT id FROM dependants ORDER BY id;
